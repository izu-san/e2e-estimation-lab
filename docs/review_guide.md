# 見積もり結果のレビュー手順

AIが作った見積もりを、人が確認して承認するための手順です。
AIの見積もりは**下書き**です。
意味レビュー（別のAIによる見直し）を通っていても、
人が確認するまで「確定」とは扱いません。

## 1. 確認する順序

1. `summary.md` で全体像をつかむ。
   先頭の「結論」（標準の人時と幅）と「人がやること（優先順）」から読む。
   内部用語の説明は「状態の見方」、検証の詳細は末尾の「技術的な詳細」にある
2. 「確認事項」「条件付きの仮定・条件」を読み、顧客に確認すべき点を整理する
3. `annotated/<元ファイル名>_見積付き.xlsx` を開き、
   元の項目書の並びで項目ごとの結果を通して見る（[2.5](#25-見積付きの項目書annotatedの使い方)）
4. 「意味レビュー」シートの指摘と、その対応を確認する
5. 「レビュー」シートで、ケースごとの判定を記入する
6. 結果を記録し、必要なら承認する（`mark-review --by human`）

## 2. 状態の読み方

| 見えているもの | 意味 | 人がすること |
|---|---|---|
| 難易度 Low / Mid / High | 5軸の点数から機械的に決まった難易度 | 5軸の点数と根拠が妥当かを確認する |
| 難易度 空欄（null）・要確認 | AIが判断できず、工数を出していない | 質問の内容を確認し、顧客に聞くか仮定を置く |
| Impossible | 実現不可と確認済みのもの。工数は出さない | 理由・根拠・代替案が妥当かを確認する |
| 条件付き | 「この仮定が成り立つなら」の数字 | 仮定が現実的かを確認する。成り立たないときは再見積もりの対象 |
| 別見積・対象外 | 今回の見積もりに含めない | 範囲の切り方が合っているかを確認する |
| 一部未算定 | 工数を出せなかった項目が残っている | 残りの項目を、人が見積もるか、条件を詰める |

## 2.5 見積付きの項目書（annotated）の使い方

`runs/<run_id>/annotated/<元ファイル名>_見積付き.xlsx` は、
元の項目書のコピーです。
各項目の行の右側に、次の4列が追記されています。
元ファイルは変更されません。

| 列 | 内容 |
|---|---|
| 自動化難易度 | 低 / 中 / 高 / 不可能。判定できなかった項目（要確認）は「判定不可」 |
| 自動化工数(標準) | 標準の工数。要確認の項目は空欄 |
| 懸念点 | 置いた仮定、要確認の質問。内部IDは出さず、Excelだけで読める日本語で書かれる |
| 備考 | 工数の幅（下限〜上限）、条件付き・要確認の注記、統合・分解の説明、見積もり対象外の理由 |

使いどころと注意:

- **顧客や担当者に見せて、項目ごとの感覚と合うかを確かめる**のに向いています。
  「レビュー」シートはケース単位で、元の項目書の並びとは違うためです。
- 懸念点が空でない行は、仮定や確認事項が付いています。
  備考の「条件付き」「要確認」と合わせて、先に拾ってください。
- 複数の項目を1つのケースにまとめたときの工数は、
  **先頭の項目の行だけ**に載ります。
  他の項目の行が空欄でも、工数が漏れているわけではありません。
  備考に「合わせて1つの見積もりにまとめ」と書かれています。
- 1つの項目を複数のケースに分解したときは、
  工数は合算されて載ります（備考に分解数が出ます）。
- **共通作業（ログイン処理、ページオブジェクトなど）の工数は含まれません。**
  項目に紐づかないためです。
  この列の合計は、`summary.md` の総計と一致しません。
  総計は `summary.md` と `estimate.xlsx` で確認してください。
- 構成案が複数あるときは、各セルに `［構成案名］` ごとの値が改行で並びます。
- 判定の記入や承認の記録は、
  このファイルではなく「レビュー」シート（3章）と `mark-review`（5章）で行います。
  このファイルは読むためのものです。
- `.xlsx` / `.xlsm` の入力だけが対象です。
  マクロは保持も実行もされず、`.xlsx` で出ます。

## 3. 「レビュー」シートの記入

`estimate.xlsx` の「レビュー」シートには、1ケースにつき1行で、次の列があります。

| 列 | 内容 |
|---|---|
| 構成案 / case_id | どの案のどのケースか |
| 原項目 | 元の項目書でのテスト項目名 |
| 分解/統合・理由 | AIが原項目をどうケースにしたか、その理由 |
| 手順 / 期待結果 | AIが整理した手順と期待結果 |
| 5軸 / 難易度 | 5軸の点数と、そこから決まった難易度 |
| AI理由 | 採点の理由 |
| **レビュー判定(OK/NG)** | **人が記入**。AIの判断に同意なら OK、そうでなければ NG |
| **正しい値** | **人が記入**。NGの場合、正しいと考える難易度や点数、分け方 |
| **コメント** | **人が記入**。理由や気づき |

### 確認の観点

**ケースの分け方（分解/統合）**
- 項目書のテスト項目が漏れていないか。説明行や凡例がケースになっていないか。
- 1つの項目を、独立して実行できない単位に分けすぎていないか。
  逆に、別々の確認を1ケースにまとめすぎていないか。
- 重複候補は、統合先と理由が残っているか（無断で消えていないか）。

**5軸の点数**
- 点数の根拠として挙げられたセルが、実際に項目書にあり、内容が合っているか。
- 基準Excelの「判定基準」シートの条件（1点・2点・3点）に当てはまっているか。
- 共通部品（ログイン処理・ページオブジェクトなど）にすでに含まれる作業まで、
  ケースの点数に加えて二重に数えていないか。
  - 共通のデータ準備・後片付けを呼ぶだけのケースは、AX-05は1点（COST-11）。
  - 共通の業務フローを呼ぶケースは、
    ケース固有の画面・分岐だけでAX-01を数える（COST-12）。

**共通作業**
- 画面の数（PAGEの数量）が、項目書とサイトの実態に合っているか。
- 「1式」の種別（BASE、RUN、DOC）が、URLの数やブラウザーの数で増えていないか。
- 同じ要素が複数の作業に重複して計上されていないか。

**確認事項・仮定**
- AIが置いた仮定が、現実的か。顧客に確認が必要なものはどれか。
- 項目書にない情報を、他の資料や推測で補っていないか。

### 判定の目安

- 難易度が1段階違うだけで、判断が分かれる境界ケースは、無理にNGにせず、
  コメントに理由を残せば足ります。
- NGが多いパターン（例: 画面の数え方が毎回違う）は、
  基準の曖昧さが原因のことが多いです。
  個別に直すのではなく、
  基準の担当者に伝えてください（[standards_update.md](standards_update.md)）。

## 4. 意味レビューの指摘の確認

「意味レビュー」シートには、別のAIが出した指摘と、
作成側AIの対応（`resolution`）が並びます。

| 対応（status） | 意味 | 人がすること |
|---|---|---|
| fixed | 指摘を受けて成果物を修正した | 修正内容が妥当かを確認する |
| question | 確認事項として質問に回した | 質問が適切か、誰が答えるかを決める |
| rejected | 指摘は当たらないと判断した | 理由（基準や原資料の根拠）が納得できるかを確認する |
| deferred | 今回は直さない（回答待ちなど） | 後で対応するか、判断する。状態に「未対応N件」と表示される |

AIが「当たらない」と判断（rejected）したものは、特に人の目で確認してください。
AIが自分の誤りを認めないこともあります。

## 5. 確認した記録を残す

レビューが終わったら、実施した人の名前を記録します。

```bash
scripts/estimator mark-review --run <run_id> --by human --reviewer <名前>
```

- `summary.md` と `validation.json` の `semantic_review_status` が「人確認済」になります。
- 人の確認は、記録した**後に**見積もりを変更しても、
  状態が自動では変わりません（AIレビューの記録は「レビュー記録後に見積もり変更」と表示されますが、人の確認にはその表示がありません）。
  記録後に再計算などをしたときは、変更部分を見直して、もう一度記録してください。
- この記録は、人が行う操作です。AIには実行させません。

## 6. 修正が必要なとき

NGのケースを直したい場合は、次の方法があります。

| 状況 | 対応 |
|---|---|
| 特定のケースの採点だけ直したい | Claude Codeで `/estimate-e2e --run <run_id>` を実行し、直したい内容を伝える。AIが `ai/assessments.json` を修正して、再計算する |
| ケースの分け方が根本的に違う | 項目整理からやり直す。下流の工程（共通設計・採点）も再確認が必要になる |
| 同じ種類の誤りが何件も出る | 基準の曖昧さが原因の可能性がある。基準の担当者に伝える |
| 計算結果だけ違う（数字がおかしい） | `estimate.json` を手で直さず、`scripts/estimator calculate --run <run_id>` で再計算する |

`ai/*.json` や `estimate.json` を手作業で直接編集することは、
避けてください（変更が検出され、状態が `modified` になります）。
