## 結論

テスト項目書の読解、テストケースへの整理、基準の当てはめ、
根拠の記録という作業は、AIで代替できる見込みが立った。
人が最終確認する前提であれば、このPoCの目標は達成した。

- 項目書1冊（20ケース）につき約15分で、
  AIが人の手を介さずに見積もりの下書き・確認事項・意味レビューまで作った。
- 同じ内容を6種類の書式で書いた項目書で、
  合計工数（標準）の差は 184〜199h（7.5%）に収まった。
- 工数の計算は専用ツール（ハーネス）が行い、AIは数値を書かない。
  点数ごとに項目書と基準のセルを根拠として残し、計算は再実行で照合できる。

一方で、AIだけでは完結しない。
見積もりの正しさの確認、基準の線引きの決定、「条件付き」「要確認」の判断、
最終承認は人が担う。
また、
**見積もりの正しさ（熟練者の見積もりや実績工数との一致）は今回測っていない。**
測ったのは、
書式や実行回数が違っても結果がそろうか（一貫性）だけである。

**技術検証の完了にあたっての扱い（2026-10-12 決定）：** 次の2点は、
現時点では仮のまま今後の検討課題として持ち越す。
いずれも技術検証の完了条件にはしない。

- 基準の仮ルール（COST-11〜13、BOUND-15〜19）は、基準の担当者による確定を待つ。
- 見積もりの正しさ（熟練者の見積もり・実績工数との照合）は、実用化の判断前に行う。

## 目的と検証の範囲

Excelのテスト項目書からPlaywright自動化の構築工数を見積もる作業を、
AIにどこまで任せられるかを確かめた。

| 項目 | 内容 |
| --- | --- |
| 対象サイト | [AutomationExercise](https://www.automationexercise.com)（練習用のECサイト） |
| 項目書 | 同じテスト項目20件を書いた6形式（詳細形式、少数列・粗粒度、横持ち、複数行・結合セル、IDなし・重複候補、複数シート・説明混在） |
| 基準 | 基準Excel 2冊（個別ケースの5軸採点と工数標準、共通部品の種別と難易度別の工数表）。v0.1 |
| AI | Claude Code（見積もり実行は Sonnet 5.5）。保護モードで人の操作なしに実行 |
| 測り方 | ① 6形式の結果の最小と最大の差（合計の標準工数）、② 原IDごとの難易度の食い違い件数、③ 同じ形式を2回実行したときの差 |
| 許容幅（仮） | 合計の差10%以内、難易度の食い違い2件以内 |

基準の曖昧な線引きは、
PoC用の仮ルールとして基準Excelに追記した（個別基準 COST-11〜13、共通基準 BOUND-15〜19）。
これらは人が確定させる必要がある（「課題」参照）。

## 仕組み

AIは意味の判断だけを行い、
計算・検証・出力はハーネス（`scripts/estimator`）が行う。

1. ハーネスが項目書と基準Excelを読み取り、座標つきの原文と基準の文章を用意する。
2. 対象サイトを閲覧できる案件では、
   ハーネスが対象サイトを「見るだけ」で調査する（ページを開くだけで、クリック・入力・送信はしない）。
3. AIが判断を工程ごとにJSONファイルとして書き、
   工程ごとに検証ツールがルールと照合する。
   1. 項目整理：原項目とテストケースの対応、未確定部分の保留
   2. 画面一覧：案件で扱う画面を一度だけ確定させる
   3. 共通設計：PAGE（画面操作）・FLOW（業務フロー）などの共通部品と、その利用ケース
   4. 確認事項：質問・仮定・前提の扱い
   5. 採点：5軸の点数と共通部品の難易度。根拠のセルを付ける
4. ハーネスが基準Excelの値で工数を計算し、`estimate.xlsx`、`summary.md`、
   元の項目書に難易度・工数・懸念点・備考を追記した `annotated/*_見積付き.xlsx` を出力する。
5. 作成とは別の会話で動くAIが意味レビューを行い、作成側が指摘ごとの対応を記録する。
6. 人が条件付き・要確認・未対応の指摘を確認し、承認する。

結果のぶれを抑える仕組みは次の3つ。

- **線引きの明文化**：曖昧な判断を基準のルールとして書き、
  検証ツールがルールどおりかを照合する。
- **事実の先行確定**：画面一覧を先に作り、後の工程はそこから選ぶ。
  閲覧できるサイトは実際に調べる。
- **手順の強制**：守るべき手順は、
  AIへの指示文ではなく検証ツールのエラーで強制する。
  保護モードでは `scripts/estimator` 以外のコマンドと、
  `runs/<id>/` 外への書き込みを拒否する。

## 測定結果の推移

AIの判断にそのまま任せた段階では、形式による合計の差は16〜30%だった。
差が10%を下回ったのは、画面を事実で確定させた後である。

| 段階 | 主な変更 | 合計の差（6形式） | 難易度の食い違い | 同じ形式2回の差 |
| --- | --- | --- | --- | --- |
| 改修前 | ― | 15.8% | ― | ― |
| 1 | 指摘対応の記録、未確定部分の保留、規則の版管理 | 30% | ― | ― |
| 2 | COST-11・12（共通部品を呼ぶケースの採点） | ケース13%、共通38% | ― | ― |
| 3 | COST-13・BOUND-15〜18（画面の数え方、部品の立て方） | 19.5% / 10.3%（2回） | 5件 / 6件 | 平均20.2h、最大36h |
| 4 | BOUND-19（PAGEの難易度を画面の特徴で決める） | 21.3% / 16.7%（2回） | 10件 / 8件 | 平均6.7h、最大15h |
| 5 | 画面一覧の工程（項目書から推定） | 19.4% | 3件 | ― |
| 6 | 対象サイトの読み取り調査 | 7.5%（184〜199h） | 6件 | ― |

- 段階4で、
  同じ形式を2回実行したときの差が平均20.2hから6.7hに縮んだ（PAGEの難易度の判定がそろった）。
- 段階5で、6形式すべての画面一覧が同じ14画面になった。
- 段階6で、合計の差が初めて許容幅の10%を下回った。ケースは7%、共通作業は8%。
- 段階5・6は各形式1回の測定で、施策の効果と実行ごとのぶれは切り分けていない。

## 人とAIの役割分担

人の担当を「見積もりの作成者」から「レビュー者・承認者」に変える形で代替する。

| 作業 | 担当 | 今回の裏づけ |
| --- | --- | --- |
| 項目書の読解・ケースの整理 | AI | 6形式すべてで同じ20ケースに整理。結合セル・IDなし・複数シートも読めた |
| 画面の特定 | AI（閲覧できるサイトはハーネスが読み取りだけで調査） | 6形式すべて、14画面で一致 |
| 基準の当てはめ（5軸採点、共通部品の難易度） | AI（検証ツールがルールと照合） | 合計の差7.5%。ただしケース単位はまだぶれる |
| 工数の計算 | ハーネス（CLI） | AIが数値を書くとスキーマ違反で拒否。再計算で一致を照合 |
| 確認事項・仮定の洗い出し | AI | 不明点は質問・条件付きとして残り、仮の数字を作らない |
| 意味レビュー（二重計上・採点根拠の見直し） | AI（作成とは別の会話） | 指摘と対応を記録。未対応があれば状態に表示 |
| 条件付き・要確認の判断、顧客への確認 | 人 | AIは判断できない点を一覧にして渡す |
| 基準の線引きの決定 | 人（基準の担当者） | ぶれが縮んだのは線引きを基準に明文化したとき。AIには決めさせない |
| 最終の内容確認と承認 | 人 | 意味レビューもAIが行うため、人の確認が前提 |

## 課題

実用化の判断を左右するのは、正しさが未検証であることと、
基準の線引きが仮であることの2点。
残りは精度や運用の課題で、今後の改善でよい。

| 課題 | 状況 | 影響 | 対応案 |
| --- | --- | --- | --- |
| 正しさが未検証 | 測ったのは一貫性だけ。人の見積もり・実績工数と比べていない | 一貫してずれている可能性が残る | 過去案件で熟練者の見積もり・実績と突き合わせる |
| 基準の線引きが仮 | COST-11〜13、BOUND-15〜19 はPoC用にAI（開発側）が決めた | 線引きが変われば工数も変わる | 基準の担当者が確定し、基準Excelに反映する |
| ケース単位のぶれ | 20ケース中6ケースで難易度が形式により変わる。AX-01（操作手順）を2点にするケースは5〜11件 | 合計は収まってもケース別の内訳は信頼しにくい | 画面一覧から、共通部品に任せた画面を除いて、ケース自身が操作する画面を機械的に決める |
| 共通部品の立て方 | FLOWの Low/Mid、MidのCOMPを立てるかが形式で割れる | 共通作業で約20hの差 | PAGEと同じく、特徴から難易度を決めるルールにする |
| 検証の範囲が狭い | 1サイト・20ケース・1モデル。最後の測定は各形式1回 | 大規模・低品質な項目書での安定性は不明 | 別サイト、数百ケースの項目書、閲覧できない案件で試す |
| AIが手順を飛ばす | サイト調査を飛ばした実行が6件中1件。指示を書き足しても同じ判断の誤りが再発した例もある | 指示文（Skill）だけでは守られない | 守るべき手順は検証ツールで強制する（調査の飛ばしは対応済み） |
| サイト調査の限界 | 読み取りだけなので、ログイン・送信後の画面は開けない（14画面中6画面は推定） | 閲覧できる案件でも推定が残る | 検証用環境での操作を許すかは案件ごとに人が決める |
| コストと人の負荷が未測定 | AIの利用料・トークンと、人のレビュー時間を測っていない | 代替の効果（削減時間）を示せない | 全部人がやる場合と、AI＋人のレビューの時間を比べる |

## 今後の進め方

実用化を判断する前に、精度の細かな改善より先に1と2を行う。

1. **正しさの検証**：過去案件の項目書でAIに見積もらせ、
   熟練者の見積もり・実績工数と比べる。
2. **基準の確定**：基準の担当者が仮ルール（COST-11〜13、BOUND-15〜19）を見直して確定する。
3. **代替効果の測定**：全部人がやる場合と、AIの下書き＋人のレビューの場合で、
   作業時間と費用を比べる。
4. **範囲の拡大**：別サイト、数百ケースの項目書、閲覧できない案件で試す。
5. **残るぶれの対策**（今後の課題）：AX-01 の操作画面の決め方と、
   FLOW・COMP の難易度のルール化。

## 用語

| 用語 | 意味 |
| --- | --- |
| ハーネス | AIの作業を支えるPythonツール一式（読み取り・検証・計算・出力）。`scripts/estimator` |
| 5軸 | 個別ケースの採点軸。AX-01 操作手順、AX-02 確認手順、AX-03 実装手段、AX-04 あいまい度、AX-05 データ準備・後処理。各1〜3点 |
| PAGE / COMP / FLOW / RUN | 共通作業の種別。PAGE=画面ごとの操作部品（ページオブジェクト）、COMP=複数画面で使う共通UI部品、FLOW=複数ケースが前提にする業務操作列、RUN=実行構成と受入確認 |
| 意味レビュー | 見積もりの分け方・採点・二重計上を、作成とは別の会話のAIが読み直して指摘する工程 |
| COST-xx / BOUND-xx | 基準Excelのルール番号。個別基準の「計上ルール」シートと、共通基準の「構成と重複防止」シートにある |
