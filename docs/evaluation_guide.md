# 評価の読み方

`scripts/estimator evaluate` が何を測り、結果をどう読むか、そして評価の基準（期待事項・許容幅）を誰がどう決めるかをまとめました。

## 1. 評価で測っていること

この仕組みの評価は、2つの観点で行います。

| 観点 | 問い | 仕組み |
|---|---|---|
| 個別の確認 | その項目書の読み取り・整理が、期待した範囲に収まっているか | 期待事項ファイルとの照合（3章） |
| 形式をまたぐ一貫性 | 同じ内容を別の書式で書いた項目書で、結果がそろうか | 一貫性グループ（4章） |

**測っていないこと**：見積もりの**正しさ**（熟練者の見積もりや実績との一致）は、この評価では測れません。評価が通っても、数字が正しいという意味にはなりません（[poc_report.md](poc_report.md)）。

## 2. 実行方法

```bash
scripts/estimator evaluate --suite evals/suites/automationexercise.yaml
```

- 評価は**すでにあるrunの結果を読む**だけで、見積もりは実行しません。先に項目書ごとに見積もりを実行しておく必要があります。
- 各項目書のrunは、「入力ファイルのハッシュが一致する最新のrun」が自動で選ばれます。runを指定したいときは、スイートの `run:` に書きます。
- 6ファイルは別案件なので、1ファイルずつ別々に実行します。
- 手順：①6つの項目書を見積もる、②`evaluate` を実行する、③結果の `status` と各チェックを読む。
- `runs/` を削除した後は、すべて `not_run` と表示されます（見積もりをやり直してください）。

### スイートの構成（`evals/suites/automationexercise.yaml`）

| 項目 | 内容 |
|---|---|
| `runs` | 項目書（`input`）と期待事項（`expectation`）の組。必要なら `run` でrunを固定する |
| `consistency_groups` | 一貫性を比べる項目書のグループ。`tolerances`（許容幅）を持てる |

## 3. 個別の確認（期待事項との照合）

### 3.1 結果の読み方

項目書ごとに `status` が付きます。

| status | 意味 |
|---|---|
| `passed` | すべてのチェックが成功 |
| `failed` | 失敗したチェックがある（`checks` に詳細） |
| `not_run` | 対応するrunが見つからない（見積もりが未実施、または入力ファイルが変わった） |
| `input_missing` | 入力の項目書が配置されていない |
| `expectation_missing` | 期待事項ファイルがない |

全体の `status` は、すべてが `passed` のときだけ `passed`、それ以外は `incomplete_or_failed` です。

### 3.2 チェックの内容

`checks` に並ぶ主な項目です。

| チェック | 内容 |
|---|---|
| `region_coverage_and_refs` | 項目書の全領域の扱いが記録され、参照が正しいか（項目整理の検証と同じ） |
| `source_items` / `source_items_mapped` / `cases` / `duplicates_recorded` / `ids_assigned` | 原項目数、ケースに対応した原項目数、整理後ケース数、重複候補数、内部ID付与数が、期待の範囲（最小・最大）に収まっているか |
| `regions_role_<役割>` | 説明・参考などの「テスト項目ではない領域」が、期待した数以上あるか |
| `topic:<名前>` | 必須の話題（キーワード）が、ケースに含まれているか |
| `question:<名前>` | 必須の確認事項（キーワード）が、質問一覧に残っているか |
| `calculation_reproducible` | 保存された `estimate.json` が、AIの成果物と基準からの再計算と一致するか。計算規則の版が変わっていた場合は、理由にそれが表示される（`calculate` の再実行で解消） |
| `machine_validation` | 機械検証の結果が期待どおりか（既定は `passed`） |

`ok: false` のチェックを見て、原因を次のように切り分けます。

- **件数が範囲外**：AIが項目を取りこぼした、または分解しすぎた可能性。`ai/normalized_cases.json` と項目書を見比べる。ただし、期待の範囲そのものが狭すぎる場合もある。
- **話題・質問のキーワードが見つからない**：実際に漏れている場合と、AIが別の言い回しで書いている場合がある。中身を読んで判断する。
- **`calculation_reproducible` の失敗**：「規則の版が変わった」ならAIの問題ではない。そうでなければ、`estimate.json` の手編集か、上流の変更を疑う。

### 3.3 「暫定」の意味

結果に `note: 期待事項が人確認済みではないため、結果は暫定です` と出ることがあります。

- 期待事項ファイル（`evals/expectations/*.yaml`）の `review_status` が `human_reviewed` でないと、その結果は「暫定」です。
- 暫定でも `passed` / `failed` は表示されますが、**期待事項そのものが正しいとは確認されていません**。「期待事項に合っている」ことと「正しい」ことは別です。
- 現状は、すべての期待事項が `human_reviewed` ではありません。したがって、**現時点の評価結果はすべて暫定**です。

| `review_status` | 意味 |
|---|---|
| `from_guide` | 設計書（旧・実装指示書）の記載だけから作った期待値 |
| `from_material` | 資料自身の記載（大規模項目書の利用案内・ケース索引シート）だけから作った期待値 |
| `unreviewed` | AIが提案した期待値の候補。人が見ていない |
| `human_reviewed` | 評価担当者が資料を見て確認済み |

### 3.4 期待事項を人が確認する流れ

期待事項は、**見積もり実行時のAIの出力から作ってはいけません**（AIの結果をそのまま正解にすると、評価の意味がなくなります）。確認の流れは次のとおりです。

1. 項目書を人が読み、期待値を決める：原項目数、ケース数の妥当な範囲、重複候補の数、ケースに含まれるべき業務範囲、質問に残るべき不明点。
2. `evals/expectations/<名前>.yaml` に書く。
3. 内容を確認できたら、`review_status` を `human_reviewed` に変更する。変更した人と日付をコメントに残すと、後から追える。

期待事項に書ける項目（`expect:`）です。

```yaml
review_status: human_reviewed
description: 前提・手順・期待結果が分離された20項目
expect:
  source_items: {min: 20, max: 20}           # 原項目数の範囲
  source_items_mapped: {min: 20}             # ケースに対応した原項目数
  cases: {min: 20, max: 30}                  # 整理後ケース数の範囲（分け方が複数妥当なら幅を持たせる）
  duplicates_recorded: {min: 1}              # 重複候補として記録された数
  ids_assigned: {min: 21}                    # 内部IDを付与した項目数
  non_test_regions_min:                      # テスト項目ではない領域（説明・参考など）の最小数
    - {role: description, min: 1}
  required_topics:                           # ケースに含まれるべき業務範囲
    - {name: ログイン, keywords: [ログイン], min_cases: 2}
  required_question_keywords:                # 質問に残るべき不明点
    - {name: 前提条件, keywords: [前提]}
  machine_validation: passed
```

- 範囲の決め方：分け方が複数妥当な場合は、人が認めた範囲を `min`〜`max` で表す。1件に固定しすぎると、妥当な別の分け方まで失敗にしてしまう。
- キーワードは、日本語の表記ゆれを考慮して複数書く。
- 現在の期待事項は薄い（例：形式01は原項目数とmachine_validationのみ）。人が確認するときに、必須の話題と質問も足すと評価の価値が上がります。
- 件数は評価資料（期待事項）にだけ書き、解析ロジックには書かないでください。

## 4. 形式をまたぐ一貫性

同じ内容を別の書式で書いた項目書は、見積もりも本来そろうはずです。その**ばらつき**を測ります。

### 4.1 比べる対象

- 各項目書の**最新のrun**どうしを比べます（`compared_runs`）。
- 最初の構成案の結果を使います。
- 前のrunのAI成果物をそのまま流用したrunは、独立した試行に数えません（`reused_ai_outputs_from`）。`independent_runs` が独立した試行の数です。
- 計算規則の版が混在していると `mixed_rule_versions: true` になります。版が違う結果どうしの比較は、公平ではありません。

### 4.2 出力の読み方

| 出力 | 内容 |
|---|---|
| `spread` | 指標ごとの最小・最大・差（`abs`）・相対差（`relative`＝差÷最大）と、形式ごとの値（`values`） |
| `item_difficulty_disagreements` | 原ID（AE-001など）ごとに、形式によって難易度が食い違うもの |
| `items_compared` | 2形式以上で比較できた原IDの数。IDが内部付与の形式（IDなしの形式05）は比較に入らない |
| `checks` / `status` | 許容幅との照合の結果（4.3） |
| `inputs` | 項目書ごとのrunの履歴と指標 |

主な指標（`spread`）：

| 指標 | 意味 |
|---|---|
| `computed_total_std` | 算定済み総計の標準工数（人時） |
| `cases_std` / `common_std` | 個別ケースの標準工数 / 共通作業の標準工数 |
| `cases` | 整理後ケース数 |
| `cases_conditional` | 条件付きのケース数 |
| `components_computed` | 算定できた共通作業の数 |
| `pending_parts` / `unresolved_items` | 保留した未確定部分 / 未解決件数 |
| `questions` | 質問の件数 |

### 4.3 許容幅（tolerances）

`consistency_groups` の `tolerances` に、評価担当者が許容幅を書きます。

```yaml
tolerances:
  max_relative_spread: {computed_total_std: 0.1}   # 合計の標準工数の相対差が10%以内
  max_abs_spread: {cases_conditional: 3}           # 条件付きケース数の差が3件以内
  max_item_disagreements: 2                        # 難易度が食い違う原IDが2件以内
```

| 状態 | 意味 |
|---|---|
| `report_only` | 許容幅が未記入。ばらつきを示すだけで、合否にしない |
| `passed` | すべての許容幅を満たした |
| `failed` | 許容幅を超えた指標がある（全体のstatusも失敗になる） |

**現在のスイートの許容幅（合計の差10%以内、条件付き件数の差3件以内、難易度の食い違い2件以内）は、PoCの仮の値です。** 根拠のある数値ではなく、評価担当者が決め直すものです（[poc_report.md](poc_report.md)）。

### 4.4 許容幅の決め方

許容幅は「どこまでのばらつきなら、人のレビューで吸収できるか」で決めます。

1. **目的から決める**：見積もりの用途（概算、提案時の見積もり、契約）によって、許されるぶれは違う。まず用途を決める。
2. **人の見積もりのぶれを基準にする**：同じ項目書を複数の人が見積もったときのばらつきが分かれば、それを上限の目安にする（AIが人より大きくぶれてよい理由はない）。
3. **現状の実測値を見る**：PoCの最後の測定では、合計の差は7.5%（184〜199h）、難易度の食い違いは6件だった。この値を知ったうえで、目標を決める。
4. **指標ごとに分ける**：合計は収まっても、ケース別の難易度は割れることがある。合計の許容と、ケース別の許容は、別々に決める。
5. **1回の測定で決めない**：各形式1回の測定は、実行ごとのぶれと施策の効果を切り分けられない。決めるときは、同じ形式を複数回実行したときの差も参考にする。
6. **決めたら記録する**：許容幅を変えたら、誰がいつ・なぜ決めたかをスイートのコメントに残す。

許容幅を後から緩めて「合格」にしないでください。基準を満たせないときは、仕組みを改善するか、許容幅の根拠を見直すかを、理由とともに判断します。

## 5. 評価を読むときの注意

- **暫定の結果は、結論に使わない**：期待事項が人確認済みでない（3.3）ことを、結果とあわせて報告する。
- **合格＝正しい、ではない**：一貫性が高くても、一貫してずれている可能性がある。正しさの検証は別に必要。
- **判断のぶれは正常**：同じ形式を2回見積もると、細かな点数は変わる。評価は「完全一致」を求めるのではなく、許容できる範囲かを見る。
- **古いrunとの比較に注意**：計算規則の版や基準が違うrunを混ぜると、比較が成り立たない（`mixed_rule_versions`）。
- **runを削除したら**：`not_run` になる。評価を再現するには、見積もりを再実行する必要がある。結果を残したい場合は、評価の出力（JSON）を保存しておく。

## 6. モデルを更新するとき（運用ルール）

AIのモデルを更新（変更）したときは、**必ず評価をやり直します。** モデルが変わると、判断の傾向が変わり、これまでの測定結果（ばらつきの大きさ、難易度の食い違いなど）が当てはまらなくなる可能性があるためです。

対象は、見積もりを実行するAIと、意味レビュー用のAIです。PoCの測定は Sonnet 5.5 で行いました（意味レビュー用AIの評価では、結果JSONにモデル名が記録されないため、実行した日付とモデル名を自分で書き留めてください）。

### 6.1 モデルの指定と記録

- モデルは Claude Code 側で選びます（セッション内の `/model` など）。このリポジトリは、見積もり用のモデルを固定していません。
- 見積もりの記録にモデル名を残すため、起動時に環境変数 `ESTIMATOR_MODEL` を設定してください（例: `ESTIMATOR_MODEL=<モデル名> scripts/start-estimate-session.sh ...`）。`manifest.json` の `environment.model` に記録されます。**未設定の場合は `null`（未記録）**になり、どのモデルの結果か後から分かりません。
- 意味レビュー用AIの評価は、`scripts/reviewer_eval.sh --model <モデル名>` でモデルを指定できます。結果JSON（`runs/reviewer_eval_*.json`）には所要時間・費用・ターン数は残りますが、**モデル名は残りません**。

### 6.2 やり直す内容

1. `uv run pytest -q`（AIを使わないテスト。念のための確認）
2. 6形式の項目書を、新しいモデルで見積もる（各形式1回。繰り返しが必要な場合は、先に確認する）
3. `scripts/estimator evaluate --suite evals/suites/automationexercise.yaml` を実行する
4. `scripts/reviewer_eval.sh --model <モデル名>` を実行する
5. 保護付き実行で挙動が変わらないかを、`scripts/permission_check.sh` で確認する

### 6.3 結果の比べ方

- 前回（PoCの最後の測定）の値と比べます：合計の差 7.5%（184〜199h）、原IDごとの難易度の食い違い 6件、画面一覧は6形式とも14画面、意味レビュー用AIの検出 7/7。
- 許容幅（4.3）を超えた場合や、前回より明らかに悪化した場合は、原因（基準の曖昧さ、手順書の効き目の変化、モデルの特性）を調べてから、モデルの採用を判断します。
- 比べるrunは、`mixed_rule_versions` が `false`（計算規則の版がそろっている）ものにします。
- 結果は [poc_report.md](poc_report.md) の測定結果の表に、日付・モデル名・測定回数を添えて追記します。
- 各形式1回の測定は、モデルの影響と実行ごとのぶれを切り分けられません。差が小さいときは、結論を急がないでください。
