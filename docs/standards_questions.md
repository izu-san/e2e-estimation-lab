# 基準Excelへの確認事項と決定の経緯

AIの判断がぶれる原因が基準Excelの曖昧さにあるとき、
ツールやSkill（AIへの手順書）側で勝手に補わず、
基準の担当者に判断を仰ぐための記録です。
回答が基準Excelに反映されたら、
Skill文書（`.claude/skills/estimate-e2e/references/`）と検証ツールの設定（`config/standards_adapter.yaml`）を見直します。

PoC（試行段階）のため、
一部は担当者の了承を得たうえで開発側（AI）が仮に決めて基準Excelへ追記しています。
**仮ルールは、基準の担当者が見直して確定する必要があります。**
確定待ちの項目は SQ-02〜04 です。

## 用語

| 用語 | 意味 |
|---|---|
| 5軸（AX-01〜05） | 個別ケースの採点軸。AX-01 操作手順、AX-02 確認手順、AX-03 実装手段、AX-04 あいまい度、AX-05 データ準備・後処理 |
| PAGE / COMP / FLOW / RUN | 共通作業の種別。PAGE=画面ごとの操作部品、COMP=複数画面で使う共通UI、FLOW=複数ケースが前提にする業務操作列、RUN=実行構成と受入確認 |
| DATA / FIX / AUTH | 共通作業の種別。DATA=テストデータの投入と復元、FIX=準備と後片付けの順序管理（fixture）、AUTH=認証処理 |
| 二重計上 | 同じ作業の工数を、ケースと共通部品の両方に計上してしまうこと |
| 意味レビュー | 見積もりの内容を、別の会話のAIが読み直して指摘する工程 |
| 検証ツール | AIが提出したJSONを機械的に検査する処理。エラーは必ず直させる。警告は注意喚起で、点数は変えない |
| EX-xx | 基準Excelの「判定例」「判定集計例」の例ID |
| COST-xx / BOUND-xx | 基準Excelのルール番号。個別基準の「計上ルール」シート、共通基準の「構成と重複防止」シートにある |

## SQ-01 共通部品を呼ぶケースの軸の点数（2026-10-10 起票・回答・反映済み）

**状況:** `runs/` の8回の実行のうち7回で、
意味レビューが同じ「二重計上の疑い」を指摘した（種別: `double_count`）。
Skillの文書に線引きを書き足しても再発している（コミット d18b098、9934834）。

- 共通のDATA / FIX（ユーザー作成・削除）を使うケースで、
  AX-05（データ準備・後処理）を一律2点にしている（形式01・03・04・05・06）。
- 共通のFLOW（カート〜注文確定）と同じ操作列を検証するケースで、
  AX-01（操作手順）を2点にしている（形式02・03・06）。

**基準の現状:** 次の記載はあるが、
「共通部品を呼ぶだけのケースの軸の点数」は書かれていない。
- 判定基準 AX-05 の2点条件「複数レコード、ファイル、ユーザー作成、
  削除・復元が必要。
  方法は既知」（判定基準!D6）
- 計上ルール COST-04（ケース固有データの指定・後処理の呼出しは個別の工数に含み、共通の準備機構の開発は別計上）
- FLOWの基準（同じ操作列をケースにも二重に実装・計上しない）
- 判定例 EX-04（会員準備を含む → AX-05 2点）、
  EX-01・EX-03（既存部品を呼ぶだけ → 1点）

**確認したいこと:**
1. ケースがDATA/FIXを呼んでユーザーを作成・削除するとき、
   ケースのAX-05は「ユーザー作成が必要」として2点か、
   「既存部品の呼出し＋固有データの指定」として1点か。
   EX-04 と EX-01・EX-03 のどちらに当たるか。
2. ケース自身の検証対象がFLOWの操作列そのもの（例: 注文確定の検証）のとき、
   AX-01はケース固有の画面・分岐だけで数えるか。
3. 上記を判定例として基準Excelに追加できるか。

**回答:**
1. 「既存部品の呼出し＋固有データの指定」として1点とする。
2. ケース固有の画面・分岐だけで数える。
3. Excelを編集できないので、可能なら開発側（AI）が追加してよい。

**反映（2026-10-10）:**
- 個別基準 `Playwright_自動化工数標準設定_v0.1.xlsx` の「計上ルール」シート A12:D13 に COST-11（回答1）・COST-12（回答2）を追記した。
  ファイルのXMLに2行を足しただけで、
  他のシート・工数・閾値・数式の保存値は変更していない。
  版の表記は v0.1 のまま。
- 判定例シートには追加していない（例1行には5軸すべての点数が要り、回答に無い他軸の点数を作ることになるため）。
- 差し替え前の原本は `~/e2e-estimation-lab-standards-backup-20261010/` に保存した。
- `config/standards_adapter.yaml` の個別基準 `approved_text_fingerprint`（基準の文章に変更がないことを確認した印）を、
  追記後の値に更新した。
- Skill（`references/assessment.md`）のAX-05・AX-01の記述を、
  COST-11・COST-12に合わせて改訂した。
- 検証ツールの警告 `AXIS_COMPONENT_OVERLAP` は維持した（共通部品と重なる軸が2点以上のとき、ケース固有に残る作業の記載を求める）。

## SQ-02 共通作業（PAGE・COMP・FLOW・RUN）の立て方（2026-10-11 起票・PoC用の仮ルールで反映）

**状況:** COST-11・12 反映後の実行（2026-10-10 21:43〜）で、
ケース工数のばらつきは13%に縮んだが、
共通作業の工数は形式間で48〜77h（38%）ばらついた。
PAGEの数量が4〜11、RUNを立てたのは6形式中3形式で、
COMP・FLOWの分け方もそろわない。
基準（BOUND-08・13）は「URL数を固定しない」「まとめるなら理由を残す」までで、
数え方を決めていない。

**仮ルール（担当者の了承を得て開発側が決定。PoC用）:** 共通基準「構成と重複防止」A16:D19 に追記した。
- BOUND-15 PAGE: 構成要素は、
  ケースまたは共通部品が自分で操作・状態取得する画面1つにつき1。
  同一URL内のモーダル等は同じ画面。
  数量の合計は画面数と一致させる。
- BOUND-16 COMP: 2つ以上のケースが使い、2つ以上の画面に現れるUIだけ。
- BOUND-17 FLOW: 2つ以上のケース（または共通部品）が前提として呼ぶ業務操作列だけ。
- BOUND-18 RUN: 複数ケースを一連で納める案件では必ず1式（単一環境の逐次実行は Low）。

## SQ-03 AX-01（操作手順）の画面の数え方（2026-10-11 起票・PoC用の仮ルールで反映）

**状況:** 同じ実行で、
会員系ケース（AE-001・002・004）のAX-01が形式により1点と2点に割れた。
合計点がLow上限付近のため、
難易度がLow/Midに分かれた（原ID別の食い違い6件中3件）。

**仮ルール（PoC用）:** 個別基準「計上ルール」A14:D14 に COST-13 を追記した。
- ケースが自分で操作する画面だけを数える（PAGEのメソッド呼出しは含める。FLOW・AUTH・DATAに任せた操作列と、判定だけの遷移先は除く）。
- 操作する画面が2つ以上、または条件分岐・ダイアログ・ファイル操作を含めば2点。
  1画面の直線的な経路は1点。
- 判定例 EX-02・EX-03 は2画面で操作する例として整合させた（EX-03 の商品追加部品はPAGEのメソッドとして扱う）。

**ツール側の対応:** AX-01に `operation_screens`（操作する画面）と `factors`（点数の要因）を書く欄を追加し、
検証ツールが期待される点数・PAGEの構成要素と照合する（警告）。
共通作業の必須種別・最小利用数も警告で照合する（アダプターの `screen_rule`・`component_rules`）。

## SQ-04 PAGEの難易度の決め方（2026-10-11 起票・PoC用の仮ルールで反映）

**状況:** SQ-02・03 反映後に各形式を2回ずつ実行（2026-10-11 00:45〜）した。
PAGEの数量は全形式で14にそろったが、
同じ形式の2回の実行で合計が最大36h違った（形式03・05）。
差はほぼPAGEのLow/Midの判定で、形式03では同じ14画面が43hと68hになった。
基準のPAGEの条件（Low「少数の単純な画面操作と状態取得」、Mid「条件分岐、動的表示、複数操作・状態の提供」）は境目が曖昧。

**仮ルール（PoC用）:** 共通基準「構成と重複防止」A20:D20 に BOUND-19 を追記した。
- 画面ごとに判定する。
  iframe・複雑な動的UI → High。
  件数・内容が変わる一覧／検索結果、モーダル・確認ダイアログ、
  ファイル操作のいずれか、
  または操作する入力・選択項目が6個以上 → Mid。それ以外 → Low。
- 難易度の違う画面を1つのPAGE部品にまとめない（BOUND-13）。

**ツール側の対応:** PAGEの判定に `screen_profiles`（画面ごとの事実）を書く欄を追加し、
検証ツールが期待される難易度と照合する（警告。アダプターの `page_rule`）。

**反映後の測定（2026-10-11 11:22〜、各形式2回）:** 同じ形式の2回の合計の差は、
平均20.2h→6.7h、最大36h→15hに縮んだ。
画面ごとの難易度はほぼ全実行で一致し、`PAGE_*` 警告は0件。
残るばらつきは、PAGEとして数える画面
（ブランド・カテゴリ一覧、アカウント作成・削除完了画面の扱い）と、
AX-01でケースが自分で操作する画面を1つと数えるか2つと数えるかだった。

## 画面一覧の工程の追加（2026-10-11、ツール側の変更）

SQ-04 の測定で残ったばらつきは、PAGEとして数える画面（10〜15）と、
AX-01でケースが操作する画面の数え方だった。
ルールの当てはめではなく、画面の特定そのものが工程ごとにぶれている。
そこで、
共通設計の前に画面一覧（`ai/screens.json`）を一度だけ確定させる工程を追加した。

- PAGEの `elements` とAX-01の `operation_screens` は、
  画面一覧の `screen_id` から選ぶ（過不足はエラー）。
- 画面の候補は `screens`（数える）か `not_counted`（同じ画面として統合した・数えない）のどちらかに必ず入れる。
- 画面の根拠は `inferred`（項目書から推定）と `observed`（対象サイトの調査結果 `survey/` で確認）を区別する。
  対象サイトを閲覧できる案件の事前調査（ページを開いて読み取るだけの調査）は、
  次の段階で追加した。
- 基準の数値・判定条件は変えていない（BOUND-15 を項目書に当てはめる手順を、Skillの `references/screens.md` に書いた）。

**測定（2026-10-11 12:31〜、各形式1回）:** 6形式すべてで画面一覧が同じ14画面（名前の表記違いのみ）になり、
PAGEの数量も全形式で14にそろった。
原ID別の難易度の食い違いは10件→3件。
合計のばらつきは21%→19%で、残りはAX-01を2点にするケースの数（5〜11件）と、
FLOW・COMPの立て方と難易度（FLOWのLow/Mid、MidのCOMPの有無）だった。

## 対象サイトの調査（survey）を使った測定（2026-10-11 16:21〜、各形式1回、`config/estimate_site.yaml`）

- 6形式とも14画面。
  調査を実行した5形式は、調査で開けた8画面を observed、
  ログイン・送信後の6画面を inferred にした。
- 合計のばらつきは 175〜217h（19%）→ 184〜199h（7.5%）で、
  許容幅（10%）を初めて下回った。
  個別ケース 24%→7%、共通作業 16%→8%。
- 原ID別の難易度の食い違いは3件→6件で、許容（2件）は超えたまま。
- 形式01では、AIが手順を飛ばして調査せずに進んだ（全画面 inferred）。
  案件設定が「閲覧できる（browsable）」なのに調査結果が無い場合は、
  画面一覧の検証でエラー（`SURVEY_MISSING`）にした。
- 1回ずつの測定なので、改善が調査の効果か、実行ごとのぶれかは切り分けていない。
