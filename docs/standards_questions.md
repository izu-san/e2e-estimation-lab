## SQ-02 共通作業（PAGE・COMP・FLOW・RUN）の立て方（2026-10-11 起票・PoC用の仮ルールで反映）

**状況:** COST-11・12 反映後の実行（2026-10-10 21:43〜）で、ケース工数のばらつきは13%に縮んだが、共通作業工数は形式間で48〜77h（38%）ばらついた。
PAGE の数量が4〜11、RUN を立てたのは6形式中3形式、COMP・FLOW の分け方もそろわない。基準（BOUND-08・13）は「URL数を固定しない」「まとめるなら理由を残す」までで、数え方を決めていない。

**仮ルール（ユーザーの了承により Claude が決定。PoC用）:** 共通基準「構成と重複防止」A16:D19 に追記。
- BOUND-15 PAGE: 構成要素は、ケースまたは共通部品が自分で操作・状態取得する画面1つにつき1。同一URL内のモーダル等は同じ画面。数量の合計は画面数と一致させる。
- BOUND-16 COMP: 2つ以上のケースが使い、2つ以上の画面に現れるUIだけ。
- BOUND-17 FLOW: 2つ以上のケース（または共通部品）が前提として呼ぶ業務操作列だけ。
- BOUND-18 RUN: 複数ケースを一連で納める案件では必ず1式（単一環境の逐次実行は Low）。

## SQ-04 PAGE の難易度の決め方（2026-10-11 起票・PoC用の仮ルールで反映）

**状況:** SQ-02・03 反映後に各形式を2回ずつ実行（2026-10-11 00:45〜）。PAGE の数量は全形式14にそろったが、
同じ形式の2回の実行で合計が最大36h違った（03・05）。差はほぼ PAGE の Low/Mid の判定で、03 では同じ14画面が 43h と 68h になった。
基準の PAGE の条件（Low「少数の単純な画面操作と状態取得」、Mid「条件分岐、動的表示、複数操作・状態の提供」）は境目が曖昧。

**仮ルール（PoC用）:** 共通基準「構成と重複防止」A20:D20 に BOUND-19 を追記。
- 画面ごとに判定。iframe・複雑な動的UI → High。件数・内容が変わる一覧／検索結果、モーダル・確認ダイアログ、ファイル操作のいずれか、
  または操作する入力・選択項目が6個以上 → Mid。それ以外 → Low。
- 難易度の違う画面を1つの PAGE 部品にまとめない（BOUND-13）。

**ハーネス側:** PAGE の判定に `screen_profiles`（画面ごとの事実）を書く欄を追加し、検証器が期待難易度と照合する（警告。アダプター `page_rule`）。

**反映後の測定（2026-10-11 11:22〜、各形式2回）:** 同じ形式の2回の合計の差は平均20.2h→6.7h、最大36h→15hに縮んだ。

（ブランド・カテゴリ一覧、アカウント作成・削除完了画面の扱い）と、AX-01 でケースが自分で操作する画面を1つと数えるか2つと数えるか。

## 画面一覧の工程の追加（2026-10-11、ハーネス側の変更）

SQ-04 の測定で残ったばらつきは、PAGE として数える画面（10〜15）と、AX-01 でケースが操作する画面の数え方だった。
ルールの当てはめではなく、画面の特定が工程ごとにぶれている。そこで、共通設計の前に画面一覧（`ai/screens.json`）を一度だけ確定させる工程を追加した。
- PAGE の `elements` と AX-01 の `operation_screens` は画面一覧の `screen_id` から選ぶ（過不足はエラー）。
- 画面の候補は `screens` か `not_counted`（同じ画面として統合・数えない）のどちらかに必ず入れる。
- 画面の根拠は `inferred`（項目書から推定）と `observed`（対象サイトの調査結果 `survey/` で確認）を区別する。
  対象サイトを閲覧できる案件の事前調査（playwright-cli による読み取りだけの調査）は次の段階で追加する。
- 基準の数値・判定条件は変えていない（BOUND-15 を項目書に当てはめる手順を Skill の `references/screens.md` に書いた）。

**測定（2026-10-11 12:31〜、各形式1回）:** 6形式すべてで画面一覧が同じ14画面（名前の表記違いのみ）になり、PAGE の数量も全形式14にそろった。
原ID別の難易度の食い違いは10件→3件。合計のばらつきは21%→19%で、残りは AX-01 で2点にするケースの数（5〜11件）と、
FLOW・COMP の立て方と難易度（FLOW の Low/Mid、Mid の COMP の有無）。

## 対象サイトの調査（survey）を使った測定（2026-10-11 16:21〜、各形式1回、config/estimate_site.yaml）
- 6形式とも14画面。調査を実行した5形式は、調査で開けた8画面を observed、ログイン・送信後の6画面を inferred にした。
- 合計のばらつきは 175〜217h（19%）→ 184〜199h（7.5%）で、許容幅（10%）を初めて下回った。個別ケース 24%→7%、共通作業 16%→8%。
- 原ID別の難易度の食い違いは 3件→6件で、許容（2件）は超えたまま。
- 01 は手順を飛ばして調査せずに進んだ（全画面 inferred）。案件設定が browsable なのに調査結果が無い場合は、画面一覧の検証でエラー（`SURVEY_MISSING`）にした。
- 1回ずつの測定なので、改善が調査の効果か、実行ごとのぶれかは切り分けていない。
