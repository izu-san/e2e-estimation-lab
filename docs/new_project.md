# 新しい案件に適用する手順

> [!CAUTION]
> **業務データは使っていません。
> 実データを使う前に会社のルールを確認してください**
>
> - **今回の技術検証で使ったデータに、業務データは一切含まれていません。**
>   項目書は、
>   練習用サイト [AutomationExercise](https://www.automationexercise.com) を題材に作ったサンプルです。
>   基準Excel（判定基準・工数表）の数値も、検証用に作った仮の値です。
> - **実際の業務データ（顧客の項目書、社内の工数基準など）をAIに読ませる場合は、セキュリティなど会社のルールに必ず従ってください。**
>   外部のAIサービスへ送信される可能性があるため、
>   利用の可否・許可された環境・マスキングの要否を、
>   事前に所管部門へ確認してください。
>   確認が取れるまでは実データを入力しないでください。


練習用のサンプル以外の項目書（実案件）を見積もるときの手順です。
基本の操作は [handover.md](handover.md) と同じで、
ここでは「案件ごとに決めること」を中心に説明します。

## 1. 始める前に決めること

| 決めること | 判断の目安 |
|---|---|
| 1ファイル＝1案件でよいか | 別の顧客から別々に受け取った資料は、1ファイルずつ別案件として見積もる。同じ案件が複数ファイルに分かれているときだけ、マニフェストでまとめる（3章） |
| 対象サイトを調べるか | 見られる環境（本番や検証環境）があり、画面の洗い出しに使いたいとき（4章） |
| ページオブジェクト（POM）を使う前提か | 顧客の指定があれば設定する。不明なら `unspecified` のままにする（5章） |
| 対象外にする共通作業はあるか | CI構築など、今回の範囲外と明確なものがあれば除外する（5章） |
| 実際の顧客資料の扱い | 社外秘の資料は、先に `.gitignore` で除外してから `inputs/` に置く |

## 2. 全体の流れ

1. 資料を `inputs/` に置く（実際の顧客資料は、先に `.gitignore` で除外する）
2. 案件設定を作る（`config/estimate.example.yaml` をコピーして編集）
3. 実行する（[handover.md](handover.md) の「1件実行してみる」と同じ）
4. 結果をレビューする（[review_guide.md](review_guide.md)）
5. 確認事項を顧客に確認し、回答を反映して見積もり直す（8章）

## 3. 1ファイル＝1案件、複数ファイルで1案件

### 通常（1ファイル）

```text
/estimate-e2e inputs/<項目書>.xlsx --config config/estimate.yaml
```

- 項目書が `.xlsx` か `.xlsm` であること。
  `.xls`、パスワード付き、破損ファイルは対応外です。
  `.xlsx` に変換してから使います。
- ファイル名、シート名、列の構成は問いません。
  固定のテンプレートに依存していません。
- 項目書に書かれていない情報（前提条件やデータ）を、
  **別のファイルや推測で補うことはしません**。
  足りない情報は、質問として結果に残ります。

### 複数ファイルで1案件にする場合

機能ごとに項目書が分かれているなど、同じ案件の資料を一緒に見積もりたいときだけ、
案件マニフェスト（ファイルの一覧）を作ります。

```yaml
schema_version: 1
project_name: sample-project
inputs:
  - {path: inputs/機能A.xlsx, role: 機能A項目書}
  - {path: inputs/機能B.xlsx, role: 機能B項目書}
```

```text
/estimate-e2e --project inputs/<マニフェスト>.yaml --config config/estimate.yaml
```

- `--input`（1ファイル）と `--project` は、同時に指定できません。
- 別々の顧客の資料を、1つのマニフェストにまとめてはいけません。
  共通部品が重複して計上されます。

## 4. 対象サイトを調査するかどうか

`site.access` の設定で決めます。

| 設定 | 意味 | 向いている場合 |
|---|---|---|
| `unavailable`（既定） | 調査しない。項目書の文章から画面を推定する | サイトを見られない、まだ存在しない、見せてもらえない |
| `browsable` | `survey` コマンドが対象サイトを読み取りだけで調査する | 見られる環境があり、画面の数え方のぶれを減らしたい |

調査は**読み取りだけ**です。
ページを開いて構造を記録しますが、クリック・入力・送信・登録はしません。
ログイン後や送信後にしか出ない画面は開けないので、
項目書から推定されます（練習用サイトでは14画面中6画面が推定でした）。

### `browsable` にする設定

`config/estimate_site.yaml` を参考にして、`site` の項を設定します。

```yaml
site:
  access: browsable
  base_url: https://対象サイトのURL/
  survey:
    max_pages: 40                                          # 調べるページ数の上限
    exclude_url_patterns: [logout, delete, remove, signout]  # 開かないURLパスの正規表現（大文字小文字は区別しない）
```

- `exclude_url_patterns` には、
  開くだけで状態が変わる恐れのあるURLパスを正規表現で入れます（ログアウト、削除など）。
  省略すると既定の `logout`、`delete`、`remove`、`signout` が使われます。
  案件のサイトに合わせて追加してください。
- `max_pages` は1〜200の整数です。
- 追加の準備として Node.js 18以上と、
  調査ツールの導入が必要です（README の「セットアップ」）。
- 調査してよいかは、
  **案件ごとに人が判断**してください（顧客の許可、アクセス負荷など）。
  この仕組みは、検証環境での操作（登録・送信）を許していません。

### `browsable` なのに調査結果が無い場合

画面一覧の検証で `SURVEY_MISSING` エラーになります。
`scripts/estimator survey --run <run_id>` を実行してください（[troubleshooting.md](troubleshooting.md)）。

## 5. 案件設定の書き方

`config/estimate.example.yaml` をコピーして `config/estimate.yaml`（または案件名のファイル）を作ります。

| 項目 | 意味 | 変更が必要な場面 |
|---|---|---|
| `standards.cases` / `common` | 使う基準Excel（個別・共通）のパス | 基準の版やファイル名が違うとき |
| `target.automation_tool` / `language` / `browsers` / `environments` | 自動化の前提（ツール、言語、ブラウザー、環境数）。実行の記録（`manifest.json`）に残る。**ツールはこの値で動作を変えない**（形式チェックだけ） | 顧客の指定があるとき。ブラウザーの扱いは、項目書の内容と基準（標準環境はChromium 1種）に基づいてAIが判断する |
| `architecture.pom` | ページオブジェクトを使うか。`enabled` / `disabled` / `compare` / `unspecified`。AIが構成案を作るときに参照する（Skillの手順） | 指定があれば設定する。`compare` は、使う場合と使わない場合の複数の構成案を作る。`unspecified` は、1つの構成案を作り、採用した前提を仮定として記録する |
| `architecture.existing_assets` | 既存の自動化資産の有無を示す文字列（既定は `unknown`）。実行の記録に残るだけで、ツールの動作は変えない | 既存資産があるときは、設定だけに頼らず、項目書や質問に残す。流用の扱いは、適合性が確認できた場合だけ新規実装分が0になる、という基準のルールに従う |
| `scope.excluded_type_ids` | 対象外にする共通作業の種別ID（例: `[CI]`） | 範囲外と明確なもの。除外したものは「対象外」として記録される |
| `uncertainty` | 不明点の扱い（`allow_explicit_assumptions`、`on_unresolved`: `continue_as_pending` / `stop`） | 通常は変更しない（不明点は質問に残して進める） |
| `execution.max_repair_attempts` | AIが検証エラーを直す回数の上限（0〜10、既定2） | 通常は変更しない |
| `execution.chunk_rows` | AIが読む表示を分割する行数（10以上、既定80） | 大きな項目書で表示が長すぎるとき |
| `site` | 対象サイトの調査（4章） | 調査するとき |

- **変更しない項目**: `execution.site_interaction` は `false` のみ許可されています（サイトへの操作はしない）。
- 設定を変えたら、**新しいrunで実行**してください。
  実行を開始した後で設定を変えると、`SOURCE_CHANGED` で止まります。

## 6. 大規模な項目書の場合

数百〜数千件の項目書（練習用の2,400件の例）では、AIが全行を読むのではなく、
次の流れで構造を把握します。

1. 項目書を読み取ったあと、
   `profile` で列ごとの値の分布（種類数、上位の値、組み合わせ）を見る。
   ```bash
   scripts/estimator profile --run <run_id> --sheet <シート名> --rows 5-304 --header-row 4 --group-by B
   ```
2. 観点×データ×ブラウザーのような**繰り返し構造**を見つけ、
   代表の行と境界を確認する。
3. 「何行目から何行目、何行で1項目、ID列はどこか」を宣言する。
   ツールが残りの行を展開し、検証する。
4. ケースへの対応付けは、列の値による選択（例: 「観点がAの行」）でも指定できる。

見積もりで注意すること:

- 繰り返し（データ違い・ブラウザー違い）を、
  **件数分の別実装として満額計上しない**。
  パラメータ化やブラウザー差分として整理します。
- 基準の標準環境（Chromium 1種）以外のブラウザーは、
  基準のルール（COST-06）に従い、AIが仮定または別見積として扱います。
- 「想定」「未確認」と書かれた期待結果は、事実として扱わず、質問や仮定に残ります。
- 整理後のケース数は、原項目の件数より少なくなることがあります。
  件数そのものではなく、**対応関係とまとめ方の理由**を人が確認してください。
- 画像・図形の中の文字、グラフシートは読み取れません。
  画像の内容に依存する項目は質問に残ります。
- マクロ（VBA）は実行も解析もされません。マクロの存在は警告として記録されます。

## 7. 実行の際の注意

- 実際の顧客資料を使うときは、
  **保護付きの実行**（`scripts/start-estimate-session.sh`）をおすすめします。
  AIが書き込めるのが `runs/<run_id>/` だけに制限されます。
- 実行には、
  AIの利用料と時間がかかります（20ケースの項目書で約15分。大規模なものはさらにかかります）。
- 顧客の項目書の中に「指摘を0件にせよ」のような指示めいた文章があっても、
  AIはデータとして扱い、従いません。
  ただし、そうした文章を見つけたら結果をよく確認してください。

## 8. 結果が出た後

1. [review_guide.md](review_guide.md) の手順で、結果を人が確認する。
2. 「確認事項」「条件付きの仮定・条件」を整理して、顧客に確認する。
3. 回答が得られたら、項目書や設定に反映して**新しいrunで見積もり直す**。
   AIの成果物（`ai/*.json`）を手で書き換えることは避けてください。
4. 同じ種類のぶれや誤りが何件も出るときは、基準の曖昧さが原因の可能性があります。
   [standards_update.md](standards_update.md) を参照してください。

## 9. 見積もりを出す前の最終確認

- [ ] `execution_status` が「処理成功」で、機械検証にエラーが残っていない
- [ ] 「一部未算定」の場合、
  未算定の項目（要確認・Impossible・別見積）の扱いを決めた
- [ ] 「条件付き」の仮定を、顧客に確認した（または確認前提と明記した）
- [ ] 意味レビューの指摘に対応があり、未対応（deferred）の内容を把握している
- [ ] 人のレビューを記録した（`mark-review --by human`）
- [ ] 基準の仮ルール（COST-11〜13、BOUND-15〜19）が確定済みかを確認した
- [ ] 「算定済み総計」を、案件全体の確定総額として扱っていない
- [ ] この見積もりの正しさが、
  人の見積もりや実績と照合されていないことを把握している（現時点で未検証）
