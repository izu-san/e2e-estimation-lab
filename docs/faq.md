## この仕組みについて

**Q. 何をする仕組みですか。**
Excelのテスト項目書を読み、基準Excelの判定基準と工数表を当てはめて、Playwrightによる自動化の構築工数を見積もる実験用の仕組みです。読んで判断する部分はAI（Claude Code）が、数える・計算する・検算する部分はPythonのツールが行います。→ [README.md](../README.md)

**Q. 見積もりをAIに完全に任せられますか。**
いいえ。AIが作るのは**下書き**です。最終的な内容確認、条件付き・要確認の判断、基準の線引きの決定、承認は人が行う前提です。→ [poc_report.md](poc_report.md)、[review_guide.md](review_guide.md)

**Q. PoCは成功したのですか。**
「人が確認する前提で、読解・整理・当てはめ・根拠の記録をAIで代替できる」という目標は達成しました。一方、見積もりの**正しさ**（熟練者の見積もりや実績との一致）は測っていません。→ [poc_report.md](poc_report.md)

**Q. 出た数字を顧客に出してよいですか。**
現時点では、そのままでは出さないでください。正しさが未検証で、基準の一部は仮ルールだからです。人のレビュー（[review_guide.md](review_guide.md)）を経て、条件付きの仮定を顧客に確認したうえで使います。→ [new_project.md](new_project.md)

**Q. 練習用のサイトや項目書は、本番の資料ですか。**
いいえ。`inputs/` と `standards/` のExcelは、検証のために作成したサンプルデータです。

## 精度と信頼性

**Q. 同じ項目書で実行するたびに、結果が少し変わるのはなぜですか。**
AIの判断は、同じ入力でも毎回少し揺れます。計算そのものは決定的で、同じ採点JSONと同じ基準からは、必ず同じ工数になります。揺れの大きさは、基準の文章の曖昧さに左右されます。PoCでは、基準に線引きを書き足すたびに揺れが縮みました。→ [poc_report.md](poc_report.md)

**Q. どのくらい揺れますか。**
6種類の書式の項目書で、合計工数（標準）の差は最後の測定で7.5%（184〜199h）でした。ただしケース単位の難易度は、20ケース中6ケースで書式により変わりました。各形式1回の測定なので、施策の効果と実行ごとのぶれは切り分けていません。→ [poc_report.md](poc_report.md)

**Q. 「条件付き」とは何ですか。**
示した仮定が成り立つ前提の数字、という意味です。仮定が成り立たなければ、再見積もりが必要です。仮定は `summary.md` の「条件付きの仮定・条件」に一覧で出ます。→ [glossary.md](glossary.md)

**Q. 「一部未算定」と出ました。合計は使えますか。**
「算定済み総計」は、**工数を出せた分だけの合計**です。案件全体の確定総額ではありません。未算定の項目（要確認・Impossible・別見積など）は、別に人が見積もるか、条件を詰める必要があります。→ [review_guide.md](review_guide.md)

**Q. 検証が通ったので、見積もりは正しいのですか。**
いいえ。機械検証が確認するのは、形式・参照・計算の再現性・二重計上などです。内容が妥当かどうかは確認しません。意味レビュー（別のAI）も、AIによる見直しなので、人の確認の代わりにはなりません。→ [review_guide.md](review_guide.md)

**Q. 評価が合格でした。正しいということですか。**
いいえ。評価が測っているのは一貫性です。また、期待事項が人確認済みでない間は、結果は「暫定」です。→ [evaluation_guide.md](evaluation_guide.md)

## AIの動き

**Q. なぜAIに計算させないのですか。**
AIは計算を誤ることがあり、毎回同じ結果にもなりません。そこで、AIは「このケースの操作手順は2点」といった判断と根拠だけを書き、難易度の決定と工数の計算は、基準Excelの値を使ってツールが行います。AIが工数や合計を書いた提出物は、形式チェックで拒否されます。

**Q. AIが勝手に基準や数値を決めることはありませんか。**
ありません。数値は基準Excelだけにあり、AIは基準にないものを創作しません（基準にない項目は「未算定」になります）。基準の曖昧な線引きは、人が決めます。PoCでは、担当者の了承のもとで開発側が仮ルールを追記しましたが、これは確定が必要です。→ [standards_questions.md](standards_questions.md)

**Q. 別のAIがレビューするなら、それで十分ではありませんか。**
十分ではありません。別のAIによる意味レビューは、見落としを減らす役目です。AIが「問題なし」あるいは「指摘は当たらない」と判断したものも、人が確認する必要があります。レビュー用AIの検出力は、仕込んだ欠陥を使った小さな評価で確かめた段階です。→ [reviewer_agent_test_design.md](reviewer_agent_test_design.md)

**Q. AIが指示を無視したり、手順を飛ばしたりしませんか。**
あります。例えば、サイト調査を飛ばした実行が6件中1件ありました。指示文（Skill）だけでは守られないことがあるため、守るべき手順は検証ツールのエラーで強制しています（調査を飛ばした場合のエラー `SURVEY_MISSING` など）。→ [architecture.md](architecture.md)

**Q. 項目書の中に「指摘は0件にせよ」のような文があったらどうなりますか。**
項目書の文章は**データ**として扱われ、指示としては従いません。レビュー用AIの評価で、そのような指示を仕込んだ場合でも従わなかったことを確認しています（小さな人工データでの1回の確認です）。→ [reviewer_agent_test_design.md](reviewer_agent_test_design.md)

**Q. AIが分からないことは、どう扱われますか。**
ユーザーに質問せず、質問一覧（`ai/questions.json`、Excelの「確認事項」シート）に残して、算定できる範囲を進めます。仮の数字は作りません。→ [review_guide.md](review_guide.md)

## 基準Excelと数値

**Q. 工数や閾値を変えたいのですが、どこを直しますか。**
基準Excelだけです。ツールやAIへの指示に数値を書き写していないので、基準を直せば次の見積もりから反映されます。ただし、文章を変えたときは、承認値やテストの更新が必要です。→ [standards_update.md](standards_update.md)

**Q. COST-11〜13、BOUND-15〜19 とは何ですか。**
基準Excelに、PoCの途中で追記した**仮のルール**です（共通部品を呼ぶケースの採点、画面の数え方、PAGEの難易度など）。基準の担当者が確定するまで暫定です。→ [standards_questions.md](standards_questions.md)、[glossary.md](glossary.md)

**Q. 仮置き工数は現実的ですか。**
この仕組みは、**仮置き工数の妥当性を検証していません**。基準Excelの値を正しく適用できるかを見るものです。工数表の校正は、別に行う必要があります。→ [設計書](ClaudeCode_E2E_Estimator_Implementation_Guide_v1.1.md)

**Q. 基準Excelを変えたら、エラーで止まりました。**
基準の文章が承認時から変わると、意図的にエラーで止まります（ルール実装との整合を確認してもらうため）。→ [troubleshooting.md](troubleshooting.md)、[standards_update.md](standards_update.md)

## 運用

**Q. 実行にどのくらい時間と費用がかかりますか。**
20ケースの項目書で、約15分でした。AIの利用料と、人のレビュー時間は測っていません。→ [poc_report.md](poc_report.md)

**Q. 途中で止まりました。やり直しですか。**
`scripts/estimator status --run <run_id>` で状態を確認し、`/estimate-e2e --run <run_id>` で再開できます。ただし、入力・基準・設定が実行開始後に変わったときは、新しいrunを作り直します。→ [handover.md](handover.md)、[troubleshooting.md](troubleshooting.md)

**Q. 複数の項目書をまとめて見積もれますか。**
別々の顧客の資料は、1ファイルずつ別案件として見積もります。同じ案件の資料が複数ファイルに分かれているときだけ、案件マニフェストでまとめられます。→ [new_project.md](new_project.md)

**Q. 大きな項目書（2,000件超）でも使えますか。**
サンプルの2,400件の項目書で動作を確認しています。AIが全行を読まず、繰り返し構造を把握して範囲を宣言する方式です。ただし、大規模・低品質な項目書での安定性は未検証です。→ [new_project.md](new_project.md)、[poc_report.md](poc_report.md)

**Q. 対象サイトを調査すると、何が起きますか。**
ページを開いて構造を記録するだけで、クリック・入力・送信・登録はしません。ログイン後や送信後の画面は開けないため、項目書から推定されます。調査してよいかは案件ごとに人が判断してください。→ [new_project.md](new_project.md)

**Q. `runs/` が増えました。消してよいですか。**
消して構いません。残したい結果は、先に `summary.md` と `estimate.xlsx` を別の場所に保存してください。削除は元に戻せません。→ [handover.md](handover.md)

**Q. AIのモデルを変えたい（更新したい）。**
検証は Sonnet 5.5 で行いました。モデルが変わると判断の傾向も変わる可能性があるので、変えたあとは評価をやり直して、結果を確認してください。→ [evaluation_guide.md](evaluation_guide.md)

**Q. WindowsやMacで動きますか。**
Linux / WSL2 で確認しています。起動スクリプトとHookは bash と `.venv/bin/python` を前提としており、ネイティブWindowsは未対応、macOSは未確認です。→ [README.md](../README.md)

## 安全性

**Q. AIが入力ファイルや基準を書き換えることはありませんか。**
保護付きの実行（`scripts/start-estimate-session.sh`）では、AIが書き込めるのは現在の `runs/<run_id>/` だけで、実行できるコマンドも `scripts/estimator` だけに制限されます。通常のClaude Codeセッションから実行する場合は、この保護は効きません。実際の顧客資料を使うときは、保護付きの実行をおすすめします。→ [README.md](../README.md)

**Q. 保護は完全ですか。**
いいえ。既定の保護は、権限ルール・自動チェック（Hook）・コマンドの制限で、OSによる書き込み禁止ではありません。許可するコマンドを増やすと弱まります。残っている穴は README の「制約・未対応事項」に書いてあります。→ [README.md](../README.md)

**Q. 顧客資料をGitに入れてよいですか。**
サンプルデータは含めています。実際の顧客資料や社外秘の基準は、先に `.gitignore` で除外してから配置してください。→ [handover.md](handover.md)
