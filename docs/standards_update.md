# 基準Excelを変更するときの手順

基準Excel（`standards/` の2冊）は、判定基準と工数の**正本**です。工数・閾値・ルールを変えるときは、ここだけを直します。コードやAIへの指示文に数値を書き写してはいけません。
ただし、基準を変えると、読み取り設定・テスト・AIへの手順書にも影響が出ます。この文書はその順序をまとめたものです。

変更は**開発モード**（通常のClaude Codeセッションか、AIを使わない作業）で行います。見積もりの実行中には行いません。

## 1. 変更の種類と影響

| 変更の種類 | 例 | 影響を受けるもの |
|---|---|---|
| 工数の数値の変更 | Mid の標準人時を変える | 基準の文章は変わらない。次の見積もりから自動で追従する。回帰テストの期待値は影響を受ける場合がある |
| 閾値の変更 | Low上限、High閾値を変える | 同上。許容範囲は基準内の記載に従う（Low上限は5〜7、High閾値は6〜15。いずれも整数で、Low上限 < High閾値） |
| ルール（文章）の追記・修正 | COST-xx、BOUND-xx を追加する | 文章フィンガープリントが変わる。承認値の更新と、Skill・検証ルールの見直しが必要 |
| 判定条件の変更 | AXの点数条件、総合判定の手順を変える | 計算ロジック（ルール版）の変更が必要になることがある |
| 構造の変更 | シート名・見出し・表の位置を変える | 読み取り設定（アダプター）の調整が必要 |
| 版を上げる（v0.1 → v0.2） | 基準全体の改訂 | 読み取りが対応する版の追加、回帰テストの再整備が必要 |

## 2. 基本の手順

1. **原本をバックアップする。** 変更前の2冊を別の場所にコピーし、日付を付けて保管する。
2. **Excelを編集する。**
   - 数値を設定するのは、黄色のセルだけです（基準内に記載あり）。
   - 数式のセルは、保存された計算結果だけが使われます。Excelで開いて保存し直し、計算結果が保存された状態にしてください（保存結果が無いとエラーになります）。
   - 変更後の版・日付・変更点を、基準内の版の記載に反映するか、変更履歴に残してください。
3. **読み取り確認をする。**
   ```bash
   scripts/estimator inspect-standards --config config/estimate.yaml
   ```
   工数表・閾値・判定軸・共通工数表・判定集計例が、意図したセルから読めているかを確認します。エラーや警告が出たら、次の「読み取りエラーの直し方」を見ます。
   `--show-text` を付けると、全シートの文章を座標つきで表示します。
4. **文章フィンガープリントを更新する**（文章を変えたときだけ）。
   - `inspect-standards` の出力に表示される `text_fingerprint` を、`config/standards_adapter.yaml` の該当する `approved_text_fingerprint`（個別基準・共通基準それぞれ）に書き写します。
   - 書き写す前に、**変えた文章が計算ロジックと食い違っていない**ことを確認します（次項）。この更新は「この文章とこのルール版は整合している、と人が確認した」という意味の記録です。
   - 更新しないまま実行すると、「基準の文章が承認時から変更されています」というエラーで止まります。これは意図した動作です。
5. **回帰テストの期待値を更新する。**
   - 共通基準を変えたら、`evals/regression/common_example.yaml` の `standards_sha256` を新しいファイルのハッシュに更新します。
   - ハッシュは `sha256sum standards/Playwright_汎用共通部分工数基準_v0.1.xlsx` で確認できます。
6. **テストを通す。**
   ```bash
   uv run pytest -q
   ```
   特に `tests/test_standards.py` が、判定例12件と判定集計例（下限22・標準39・上限64人時）の再現を確認します。工数の数値を意図して変えた場合は、この期待値が変わることがあります。変わる理由を確認したうえで、期待値を更新してください。
7. **新しいrunで確認する。** 変更後は、既存のrunを再開せず、新しいrunで1件実行して、結果が意図どおりに変わるかを確認します（基準が変わったrunは `SOURCE_CHANGED` で止まります）。

## 3. ルール（文章）を変えたとき

COST-xx、BOUND-xx、判定例などの文章を追加・変更したときは、次を確認します。

1. **計算ロジックに影響するか。** 影響するなら、`src/estimator/calculate.py` を修正し、`src/estimator/__init__.py` のルール版（`CASE_RULE_VERSION` / `COMMON_RULE_VERSION`）を上げます。上げ忘れは `tests/test_calc_version.py` が検出します。
2. **AIへの手順書に影響するか。** `.claude/skills/estimate-e2e/references/`（特に `assessment.md`、`common-design.md`、`screens.md`）の該当する説明を、新しいルールに合わせて直します。基準の数値は書き写さず、ルール番号で参照します。
3. **検証ルールに影響するか。** `config/standards_adapter.yaml` の検証設定（`component_overlap`、`screen_rule`、`page_rule`、`component_rules` など）が、新しいルールと食い違っていないかを確認します。
4. **経緯を記録する。** [standards_questions.md](standards_questions.md) に、何が曖昧で、誰がどう決め、どこに反映したかを追記します。

## 4. 読み取りエラーの直し方

| 症状 | 原因と対処 |
|---|---|
| 見出しが見つからない・曖昧 | 基準の見出し文字列が変わった。`config/standards_adapter.yaml` の見出し候補（`aliases` / `labels`）か `sheet_pattern` を直す。コードには数値や位置を書かない |
| 数式の保存結果が無い | Excelで開いて保存し直す（計算結果を保存する）。0や推定値で代用しない |
| 未対応の版 | 読み取りが対応する版（`supported_versions`）に追加する。対応する前に、構造とルールの差を確認する |
| 工数が「下限 ≦ 標準 ≦ 上限」でない・負数・空欄 | 基準の入力ミス。Excelを直す |
| 「基準の文章が変更されています」 | 文章を変えた。手順4で承認値を更新する（意図しない変更なら、Excelを元に戻す） |
| 「文章フィンガープリント未承認」の警告 | 承認値が未記入。実行はできる。確認が済んだら手順4で記入する |

## 5. 基準の担当者に確認するべきとき

次の場合は、開発側で勝手に決めず、基準の担当者に確認します。

- 同じ種類の判断が、実行のたびに割れる（AIが毎回違う点数を付ける）。原因が基準の曖昧さにあることが多い。
- 意味レビューが、同じ指摘を何度も出す。
- 基準にない作業や、基準の上限を超える作業が出てくる（別見積・未算定として扱い、数字を創作しない）。

PoCでは、担当者の了承のもとで開発側が仮のルールを追記した経緯があります（COST-11〜13、BOUND-15〜19）。これらは仮のものなので、本運用の前に基準の担当者が確定してください。確定後は、基準Excelの該当行に「確定」と版・日付を記録し、この手順で承認値とテストを更新します。
