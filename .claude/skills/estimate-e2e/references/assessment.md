# Stage 6: 個別ケースの判定と共通作業の難易度（assessments.json）

前提: `ai/questions.json` が検証済み（工程5）。`question_ids` は questions.json に存在するIDだけを使う。

スキーマ: `schemas/assessments.schema.json`。**工数・総合難易度・合計は書かない**（書くとスキーマエラー）。

## 個別ケース（case_assessments）
確定または仮定した共通構成を前提に、ケース×構成案（`arch_ids`）ごとに書く。同じ採点を複数案に使うなら `arch_ids` に列挙。

1. `scope`: 対象内 / 別見積 / 対象外（理由 `scope_reason`）。Web E2E以外の手段が必要なもの等。
2. `feasibility`: `impossible_confirmed` は「合意範囲で実現不可と確認済」のときだけ（理由 `impossible_reason`）。疑いだけなら `unknown`。
3. `info_sufficient`: 主要情報が不足し方針を定められないなら false（→要確認・難易度null）。
4. `axes`: 基準Excelの全軸（AX-01〜AX-05）を1〜3点またはnull。各軸に
   - `condition`: 基準のどの条件に当てはめたか（基準の文言。可能なら `standard_refs` に `cases:シート名!セル`）
   - `evidence`: 原資料の根拠（どの手順・期待結果か）
   - `assumptions`: 置いた仮定
5. `estimate_status`: 確定可能 / 条件付き（`conditions` 必須）/ 要確認。基準の規則（RULE-07・RULE-03）で決まり、検証器が照合する:
   - 仮定なし・5軸確定 → 確定可能。あいまい度（AX-04）が2点以上、または軸の `assumptions`・`conditions` があれば → 条件付き
   - 情報不足・実現性不明 → 要確認。Impossible → 確定可能（工数はnull）
6. `uses_components`: 前提にした共通作業ID。

総合難易度（Low/Mid/High）は閾値とともにCLIが基準Excelの値から決める。合計点を自分で判定しない。

### AX-05（データ準備・後処理）と共通のDATA/FIXの境界
個別ケースのAX-05は「そのケース固有の準備・後処理の重さ」を採点する。共通部品の開発時間は共通側（DATA/FIX/AUTH等）に別計上する（基準 判定基準 AX-05 の根拠欄、計上ルール COST-04）。
- 点数は基準Excelの文言と判定例だけで決める。AX-05の2点の条件は「複数レコード、ファイル、ユーザー作成、削除・復元が必要。方法は既知」（判定基準!D6）で、共通部品の有無では変わらない（共通準備部品の開発時間は別計上＝根拠欄・COST-04）。判定例は、会員準備を含む EX-04 が2点、既存ログイン部品と固定データの EX-01・商品追加部品を呼ぶだけの EX-03 が1点。基準にない割引（共通部品があるから1点）も加点も作らない。
- 根拠には、基準のどの文言・どの判定例に当たるかを書く。判定例のコメントに無いこと（例: 「共通部品があっても2点」）を判定例の内容として書かない。
- 1点にできるのは、静的データまたは既存fixtureで足り、ケース固有の復元が軽微なとき（データの指定とcleanup呼出しだけ）。
- 3点は、多段階の状態作成・共有資源の隔離・複数システム間の準備復元が**このケース固有で**必要なとき。共通側のFIX/DATAがHighでも、ケースのAX-05を自動で3点にしない。
- 二重計上の確認: 共通側に積んだ作業（DATA-xxx の実装）を、ケースのevidenceで「新規開発」として再び重く評価していないか。ケースは「共通部品を呼ぶ＋固有データを指定する」範囲だけを根拠にする。
- 迷ったら、evidenceに「どの共通部品を呼ぶか」と「ケース固有の準備・後処理」を分けて書く。

### 採点の線引きを揃える（AX-01・AX-04）
- AX-01 の「複数画面」: 画面（URLや主要な表示領域）をまたいで操作する手順は、ケース間で同じ線引きにする。一覧→詳細、検索→結果→詳細のように
  画面をまたぐものを、ケースによって1点・2点と分けない。1点にするなら同一画面内の操作とみなす理由を evidence に書く。迷ったら判定例（`cases.md` 全文）に合わせる。
- AX-04（あいまい度）: 仮定なしの点数にその軸の `assumptions` を付けない。重複統合など案件範囲の仮定は `conditions` と質問で表す
  （`AXIS_ASSUMPTION_SCORE` 警告）。
- 共通部品が持つ未解決の仮定（例: カード受理）を受け継ぐケースは、その仮定の影響を `conditions`・`question_ids` に残す。
  自分の手順・期待結果が具体的ならあいまい度は上げず、同じ仮定を使うケース間で扱いを揃える（上げるなら全員上げる）。

## 共通作業（common_assessments）
- 共通基準の**種類別の判定条件**に照らして Low/Mid/High（決められなければnull＋要確認）。
  当てはまる最も高い条件を選び、仕様に無いHigh要因を想像で加えない（COM-04）。Mid要因が複数あるだけで昇格しない（COM-05）。
- 合意した手段・権限・環境で実現不可と確認済みなら `Impossible`（`impossible_reason` に理由・根拠・解消条件・代替案。
  estimate_status は確定可能。COM-10）。不明なだけならImpossibleにしない。
- 条件付きにする場合は `conditions` に仮定・影響・再見積条件を書く（COM-09）。
- `matched_conditions` に当てはめた条件、`standard_refs` に `common:シート名!セル`、`rationale` に理由。
- `cost_owner` が自分自身の 新規/改修 作業はすべて判定する（無いと未算定）。

## 共通構成を変えたら
`common_design.json` を変更すると採点・計算は stale になる。影響する `used_by` のケースを再採点してから再計算する。

## 根拠の書き方と補足
- `evidence` のセル座標は `シート名!セル` 形式（例: `確認リスト!C3`）。`views/*.md` の座標を確認して書く。シート名なしは警告（`EVIDENCE_REF_NO_SHEET`）。
- 要確認ケースでも、判定できる軸は採点してよい（個別基準 判定例 EX-08・EX-12 は一部の軸だけ採点した要確認）。
  決められない軸は null とし、`info_sufficient: false`・要確認にする。難易度・工数は空欄になる。
- AX-05 の目安は個別基準の判定例を確認する（EX-01: 既存ログイン部品と固定データ→1点、EX-04: 会員準備を含む→2点）。
- `uses_components` は `common_design.json` の `used_by` と**完全に一致**させる（全ケースが使うBASE・RUNも含む）。食い違うと `USAGE_MISMATCH` エラー。
- 質問・仮定を起票したら、その `targets` のケース・共通作業の `question_ids` にも同じIDを書く（双方向）。同じ共通部品・前提を共有する他のケースにも影響しないか確認する。

## 基準・仮定に接地する（数値や条件を創作しない）
- 工数・人時・割合・割引・合計点・総合難易度は、AIが判断文（rationale・condition・conditions・責務の説明）に書かない。基準Excelの値の転記も独自の相場も禁止。算出はCLI（`UNSOURCED_NUMBER` エラー）。
- 点数には基準Excelのセル参照（`standard_refs`）を付ける（無いと `NO_STANDARD_REF` 警告）。基準にない条件を作らない。
- 要確認のケースでは、原資料に無い操作を「想定」「推測」で補って採点しない。決められない軸はnull（`SPECULATIVE_EVIDENCE` 警告）。
- 案件設定のPOMが未指定でPOM採用案を作るときは、PAGE作業を条件付きにして仮定を記録する（`POM_ASSUMPTION_NOT_CONDITIONAL` 警告）。
- 未解決の質問に依存する部品を使うケースを「確定可能」にしない。影響を `conditions`・`question_ids` に残す（`QUESTION_NOT_INHERITED` 警告。全ケースが使う部品は対象外）。
- 根拠で言及する部品は `uses_components` と揃える（`EVIDENCE_COMPONENT_NOT_USED` 警告）。

## 案件全体の仮定と、原資料の留意点の見落とし防止
- POM未指定・ロケーター未確認など**案件全体に効く仮定**は、質問の `targets` に構成案ID（例 `A1`）を入れる。
  `QUESTION_NOT_INHERITED` の対象外になり、全ケースを条件付きにしない。個別ケースの採点に影響する仮定だけを、
  そのケースの `question_ids`・`conditions` に書く。影響する部品（PAGE等）は従来どおり `question_ids` を持たせる。
- 採点前に、各項目の**留意点列・データ定義の「画面で確認して選ぶ」「別の〜」などの未特定語**を拾い、
  期待結果側に確認手段があるか確かめる。無ければ AX-04 を2点にして仮定を起票するか、質問にする。
  （例: 「追加の同名アカウントが作成されないこと」を期待結果で確認できない／2つ目の商品・ブランドの特定方法が無い）
- 根拠に書く画面数は `common_design.json` の PAGE の責務（画面の数え方）と揃える。

## 共通フローを呼ぶケースの AX-01（操作手順）
- ケース本体が自分で操作・判定する画面を数える。共通FLOW・AUTH・DATAが所有する実処理（カート追加、注文確定、ログイン等）は、呼び出す手順として数えず、前提の準備として扱う。
- ケース自身の検証対象がそのFLOWの操作列そのもの（例: 注文確定を検証するケース）でも、実処理はFLOWが所有する。AX-01 を2点にするなら、FLOWの操作列ではなくケース固有の画面・分岐・ダイアログを evidence に書く。
- 同じ線引きを前提準備型のケース（例: カート準備済みで削除を確認するケース）と揃える。揃わない場合は理由を evidence に書く。
- 画面を数える単位は「操作または判定を行う画面」。送信後のリダイレクト先を判定しないなら数えない。
